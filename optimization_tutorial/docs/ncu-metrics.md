# Nsight Compute metrics — working reference

Source of truth for this repo's `@metric` lines. Two parts:

- `ncu-metrics-device.txt` — every metric this machine's GPU actually supports,
  generated by `ncu --query-metrics`. Regenerate after a driver or GPU change:

      make metrics-list

- This file — the naming rules and definitions needed to read those names,
  distilled from the [Nsight Compute Profiling Guide][guide]. Consult the guide
  itself for anything not covered here.

[guide]: https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#metrics-reference

## Why device-specific matters

A metric that does not exist on the target GPU is **silently dropped** by `ncu`,
which is indistinguishable from a counter that measured zero. `optimizations.py`
therefore validates every `@metric` against the device list before profiling and
fails loudly instead.

### Optional counters

Some counters exist only on certain architectures. Prefix such a counter with
`?` and it is collected where available and skipped, with a note, where it is
not:

    @metric ?dram__bytes_read.sum | DRAMRead(B) | down | Bytes fetched from device memory

Counters without the prefix are required: if the device lacks one, the run stops
rather than reporting a misleading flat result.

### Discrete vs integrated memory

The main portability split in this repo is device memory. On a discrete GPU the
path is:

    SM -> L1TEX -> L2 (lts) -> FBPA -> DRAM

`FBPA` is the GPU's own memory controller, and `dram__*` counters are collected
there. Integrated parts — Tegra-lineage SoCs such as Orin and the Grace-Blackwell
superchips — have no GPU-owned framebuffer partition: the GPU and CPU share one
LPDDR pool across an on-package interconnect. Past L2 a request leaves the GPU's
performance-monitor domain, so `dram__*`, `fbpa__*` and `mcc__*` are all absent.

Consequences for reading the reports:

- `lts__t_sectors_op_read/write.sum` is **L2** traffic, not memory traffic. A
  sector that hits in L2 never reaches DRAM. It is the portable choice and is
  marked required.
- `dram__bytes_read/write.sum` is the true memory-traffic measure and is marked
  optional, so discrete GPUs report it and integrated ones skip it.
- Where both are present, compare them: a large L2 drop with a flat DRAM figure
  means the working set was already cache-resident and the optimization saved
  cache bandwidth rather than memory bandwidth.

To see which units your device exposes:

    awk 'NR>2 && $1 ~ /__/ {split($1,a,"__"); print a[1]}' \
        docs/ncu-metrics-device.txt | sort -u

## Name structure

    unit__(subunit)_(pipestage)_quantity_(qualifiers) . rollup . submetric

| Part | Meaning |
| --- | --- |
| `unit` | Hardware unit: `sm`, `smsp`, `l1tex`, `lts`, `dram`, `gpu` |
| `subunit` | Where in the unit, or the pipeline mode, e.g. `pipe_lsu`, `mem_shared` |
| `quantity` | What is counted: `sectors`, `requests`, `wavefronts`, `bytes`, `inst_executed` |
| `qualifiers` | Filters, e.g. `op_ld`, `op_st`, `op_atom` |

### Units seen in this repo

| Unit | Meaning |
| --- | --- |
| `gpu` | The entire GPU |
| `sm` | Streaming Multiprocessor |
| `smsp` | SM sub-partition — four per SM, each with its own warp scheduler |
| `l1tex` | L1 data cache / shared memory / texture cache |
| `lts` | One L2 cache slice |
| `dram` | Device memory — discrete GPUs only |
| `fbpa` | Framebuffer partition, the GPU's memory controller — discrete GPUs only |

### Rollups (required on counters)

`.sum`, `.avg`, `.min`, `.max` — aggregate across all instances of the unit
(all SMs, all L2 slices, ...). A bare counter name is not evaluable; that is why
every `@metric` here ends in `.sum`, `.pct`, or a `pct_of_peak_*` submetric.

### Submetrics used here

| Submetric | Meaning |
| --- | --- |
| `.pct_of_peak_sustained_elapsed` | % of peak sustained rate over elapsed cycles |
| `.pct_of_peak_sustained_active` | % of peak sustained rate over *active* cycles |
| `.pct` | Ratio expressed as a percentage |

Throughput metrics (`sm__throughput`, `gpu__compute_memory_throughput`) take only
the two `pct_of_peak_sustained_*` forms.

## Quantities — the ones that get misread

| Term | Definition |
| --- | --- |
| **request** | One command into a HW unit. On SM 7.0+, each shared-memory instruction generates exactly one request. |
| **sector** | Aligned **32-byte** chunk. A 128-byte cache line is **four** sectors. |
| **wavefront** | Work package processed in one cycle. Wavefronts are *serialized*, so extra wavefronts are extra cycles. |

Relationships are `requests:sectors = 1:N`, `wavefronts:sectors = 1:N`,
`requests:wavefronts = 1:N`.

**sectors/request** is the coalescing efficiency figure. For a 32-thread warp
reading 32-bit values the ideal is **4**; a value of 32 means every lane hit a
different sector. Used by optimization 04.

**Bank conflicts** serialize a shared-memory access into as many conflict-free
accesses as there are colliding banks. Prefer the direct counter
`l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum` over inferring
conflicts from a sectors/requests ratio. Used by optimizations 06 and 08.

## Useful commands

    ncu --query-metrics                          # every supported metric
    ncu --query-metrics-mode suffix \
        --metrics sm__inst_executed              # valid submetrics for one counter
    ncu --list-sets                              # predefined metric sets
    ncu --list-sections

## Gotchas hit while building this repo

- `--quiet` suppresses the CSV that `--csv` writes to stdout.
- Supplying `--export` also suppresses stdout CSV; read the report back with
  `ncu --import <file> --csv --page raw`.
- `ncu` writes thousands separators (`32,768`), so strip commas before `float()`.
- `gpu__time_duration.sum` is reported in **µs**, not ns.
- Metrics with `sass_` in the name are collected by software patching and carry
  much higher overhead than hardware counters.
